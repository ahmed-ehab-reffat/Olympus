# DESIGN.md — rspirv-decoration-group-resolution

## Phase 1 — Repo understanding (gate)

**Architecture (one paragraph).** `gfx-rs/rspirv` is a Rust workspace for reading, building and
writing SPIR-V (the Vulkan/OpenCL shader IR). The `spirv` crate holds generated opcode/operand
enums; `rspirv` holds four subsystems: `binary/` (byte stream <-> `dr::Module`: `parser.rs`
decodes, `decoder.rs`/`assemble.rs` encode, `disassemble.rs` renders text), `dr/` (the "debug
representation" — a flat, order-preserving `Module` struct holding `Vec<Instruction>` per section,
a `Builder` for constructing modules programmatically, and a `Loader` implementing the parser's
`Consumer` trait to build a `Module` from a byte stream), `sr/`+`lift/` (an experimental
"structured representation" that lifts `dr::Module` into a typed IR — actively under construction,
several open design threads), and `grammar/` (autogenerated instruction/operand tables). Data
flows one way through `binary -> dr -> (optionally) sr`; `dr::Module` is the stable, complete
representation most consumers use directly.

**5 top-level subsystems + boundaries:** `spirv` (opcode/enum definitions, generated) ·
`rspirv::binary` (byte-stream parse/encode/disassemble) · `rspirv::dr` (in-memory module:
`constructs.rs` types, `build/` fluent builder, `loader.rs` Consumer) · `rspirv::sr`+`lift`
(experimental typed IR, actively worked — avoid) · `rspirv::grammar` (autogenerated tables,
never hand-edited).

**3 high-entanglement zones:** (1) `dr::constructs::Module` — every subsystem reads/writes it;
(2) `dr::build::Builder` — the fluent constructor every hand-written and generated method hangs
off; (3) `binary::parser::Parser` + `dr::loader::Loader` — the `Consumer` trait pairing that turns
bytes into a `Module`, one opcode class at a time (`opcode.is_annotation()` in `loader.rs:154`
buckets `OpDecorate`/`OpMemberDecorate`/`OpDecorationGroup`/`OpGroupDecorate`/
`OpGroupMemberDecorate` all into one flat `Vec<Instruction>` called `annotations`, with zero
resolution).

**Test framework + location:** `#[test]` fns inline in the file they test (`dr/build/mod.rs`,
`dr/constructs.rs`, `dr/loader.rs`, `sr/storage.rs`) for unit-level coverage, plus
`rspirv/tests/spirv_blobs.rs` for external `.spv` corpus round-trips. New feature tests belong in
a new file under `rspirv/tests/`, built entirely through the public `dr::Builder` API (confirmed:
`Builder::decorate`, `member_decorate`, `group_decorate`, `group_member_decorate`,
`decoration_group` all already exist at `dr/build/autogen_annotation.rs:7-84` and
`dr/build/mod.rs:683`).

**Template test file cited:** `rspirv/tests/spirv_blobs.rs` — shows the `use rspirv::{binary::...,
dr, lift}` import shape and a `#[test] fn ...() { ... }` pattern; my new file follows the same
import/module shape but builds modules via `dr::Builder` instead of reading `.spv` blobs.

**Step A (TOO-EASY guard) on the survivor:** not a uniform-wrap (two distinct discard-granularity
rules + a multiplicity/polarity cross-product, not one rule repeated); not a single fully-specified
mechanical transform (the group-vs-target validity split and the "which channel" independence are

independence) survives being fully spelled out in meta.md (verified below, see trap table); not a
port of a memorized spec (SPIR-V decoration-group expansion is not a commonly-transcribed textbook
algorithm, and the resolved-output canonical form — ordering, no-dedup, diagnostics — is this
API's own invention, not the SPIR-V validator's behavior). Globally-coupled: every resolved entry
for a target depends on module-wide state (the full `defined_ids` set, the full `group_ids` set,
and the group's own decoration list), not a per-instruction local computation.

**Step B (HARDENING arsenal):** lead trap classifies as an **F-13 / S2-adjacent** discard-unit
family (mechanism below); second trap is an **F-10** capability cross-product cell (multiplicity x
polarity). CONTRACT-STATED/FIX-HIDDEN verified per-trap in §11.

**Step B-bis (failure-pattern targeting):** F-13 precondition confirmed by source: `dr::Module`
has a genuine two-tier format (`OpDecorationGroup` = base declaration at
`dr/build/mod.rs:683`; `OpGroupDecorate`/`OpGroupMemberDecorate` = amendment rows referencing it,

two independent axes on the same group id — multiplicity (any group id may be referenced by
multiple group-apply instructions) and polarity (whole-object `GroupDecorate` vs per-member
`GroupMemberDecorate`) — both usable on the SAME group in the SAME module, with no existing
constraint forcing them apart.

### 3. Public API surface

- `dr::resolve_decorations(module: &Module) -> ResolvedDecorations` — free function, the resolver entry point
- `Module::resolve_decorations(&self) -> ResolvedDecorations` — convenience method wrapping the free function, matching the existing `global_inst_iter`/`all_inst_iter` query-method convention
- `ResolvedDecorations` — opaque result type
- `ResolvedDecorations::for_target(&self, id: spirv::Word) -> &[Instruction]` — all decorations (direct + group-expanded) applying to `id`, each returned as a synthesized `OpDecorate`-shaped `Instruction`
- `ResolvedDecorations::for_member(&self, id: spirv::Word, member: u32) -> &[Instruction]` — same for `(id, member)`, each returned as a synthesized `OpMemberDecorate`-shaped `Instruction`
- `ResolvedDecorations::unresolved(&self) -> &[UnresolvedReference]` — every group-apply reference that could not be resolved
- `UnresolvedReference` — enum: `UnknownGroup { group: spirv::Word }`, `UnknownTarget { group: spirv::Word, target: spirv::Word }`, `UnknownMemberTarget { group: spirv::Word, target: spirv::Word, member: u32 }`

### 4. Canonical output form

- **Order:** for a given target (or target+member), direct decorations come first, in the order
  they appear in `module.annotations`; group-expanded decorations follow, ordered by the position
  of the `OpGroupDecorate`/`OpGroupMemberDecorate` instruction that produced them within
  `module.annotations`, and within one such instruction's expansion, by the order the group's own
  attached `OpDecorate` rows appear in `module.annotations`.
- **Dedup:** none. A decoration reachable through two different channels (e.g. applied both
  directly and via a group, or via two different groups) appears twice. `for_target`/`for_member`
  never deduplicate.
- **Target/group existence:** an id counts as defined if it is the `result_id` of any instruction
  anywhere in the module, found by scanning the whole module, not just instructions that appear
  textually before the reference — SPIR-V permits an annotation to name an id defined later in the
  module.
- **Per-entry validity:** a decoration produced by expanding a group reference is included only
  when the group named by the group-apply instruction is a declared decoration group AND the
  specific target (or target+member pair) it names resolves to a defined id. Each entry of a
  group-apply instruction is evaluated on its own.
- **Multiplicity + polarity:** the same group id may be referenced by more than one group-apply
  instruction, including both `OpGroupDecorate` and `OpGroupMemberDecorate` forms for the same
  group within one module; every reference is resolved independently against that group's own
  decorations.
- **Empty input:** `for_target`/`for_member` on an id with no decorations at all return an empty
  slice; `unresolved()` on a module with no group-apply instructions returns an empty slice.

### 5. Blind-spot pre-empts

- Forward-reference existence check (codebase-inferable but stated anyway since it silently
  changes correctness): "an id counts as defined if it is the result id of any instruction
  anywhere in the module" (§4) — pre-empts the natural single-forward-pass implementation.
- No-dedup default (against the instinct to dedupe "obviously redundant" repeats): "decorations
  reachable through two different channels are not deduplicated" (§4).
- Order-of-application stated explicitly (§4) since output is asserted with `assert_eq!` on
  ordered slices.

### 6. Description draft (meta.md, plain prose)

Draft (~185 words, under the 200 recommended / 500 hard cap):

> Add decoration-group resolution to rspirv's debug representation. `dr::Module` currently stores
> every `OpDecorate`, `OpMemberDecorate`, `OpDecorationGroup`, `OpGroupDecorate` and
> `OpGroupMemberDecorate` instruction as a flat, unresolved list in `annotations`; nothing in the
> crate expands the indirection a decoration group represents into the concrete decorations it
> contributes to each of its targets.
>
> Add a `resolve_decorations` function (and a `Module::resolve_decorations` convenience method)
> that returns a `ResolvedDecorations` value queryable with `for_target(id)` and
> `for_member(id, member)`, each returning every decoration that applies to that target or member,
> direct decorations first in module order followed by decorations contributed through group
> references in the order those references appear, then in the order of the group's own
> decorations. Decorations reachable through more than one channel are not deduplicated. An id
> counts as defined if it is the result id of any instruction anywhere in the module, not only
> ones appearing earlier. A decoration produced by expanding a group reference is included only
> when the referenced group is a declared decoration group and the specific target (or
> target-member pair) it names resolves to a defined id; `ResolvedDecorations::unresolved()`
> reports every group-apply reference that failed either check, identifying the group and the
> target or member pair involved.

### 8. Solution outline — pure-function / method helpers

- `resolve_decorations(module: &Module) -> ResolvedDecorations` ← top-level entry, description
  paragraph 2
- (internal) build `defined_ids: HashSet<Word>` from `module.all_inst_iter()` ← "any instruction
  anywhere in the module" (§4 forward-reference rule)
- (internal) build `group_ids: HashSet<Word>` from `OpDecorationGroup` result ids in `annotations`
  ← "declared decoration group" validity check
- (internal) pass 1: populate `direct: HashMap<Word, Vec<Instruction>>` and
  `member: HashMap<(Word, u32), Vec<Instruction>>` from literal `OpDecorate`/`OpMemberDecorate` ←
  base case (a group's own decorations become directly queryable at the group's id for free, since
  `OpDecorate`-targeting-a-group is just an ordinary entry in `direct`)
- (internal) pass 2: expand `OpGroupDecorate` — for each target operand, validate against
  `group_ids`/`defined_ids`, clone the group's `direct` entries with `operands[0]` rewritten to the
  real target, push (preserving order) or record `UnresolvedReference` ← discard-granularity trap
  (§11 trap 1)
- (internal) pass 2: expand `OpGroupMemberDecorate` — chunk the pair operands, validate per pair,
  synthesize `OpMemberDecorate`-shaped instructions from the group's `direct` entries (target,
  member index, decoration + extra params carried over), push or record `UnresolvedReference` ←
  discard-granularity trap + cross-product trap (§11 traps 1 and 2)
- `Module::resolve_decorations(&self)` ← thin wrapper, integration point (file footprint row 3)

No fixpoint loop needed (single deterministic two-pass resolution, not an iterate-to-convergence
transform). No recursive/cycle-trace pattern needed (decoration groups do not nest — a group's
contents are always literal `OpDecorate`, never another group reference).
