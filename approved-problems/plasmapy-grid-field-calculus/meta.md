# Add exact field calculus to Cartesian grids

A `CartesianGrid` already turns the quantities stored at its grid points into a continuous field, because `volume_averaged_interpolator` blends the eight grid points around a position with the weights of a multilinear interpolation. Nothing else in the package works with that field. Add methods that answer questions about it exactly, so that a result is the true value for the interpolated field rather than a finite difference or a sampled sum of the stored arrays. A position that falls on a boundary between cells belongs to the cell above it, and the outer edge of an axis belongs to the last cell.

All of these methods are for uniformly spaced grids and raise `NotImplementedError` otherwise, and a quantity name the grid does not carry raises `KeyError`. Positions may be given as one point or as an array of points, a plain array of positions is read in the units of the grid axes as the existing interpolators already read it, and lengths in the results are metres whatever units the axes carry. Positions off the grid come back as not-a-number, as they already do from the interpolators. Input that does not match this description raises `ValueError`, whether that is a call naming no quantities at all, an array that is neither one point nor a sequence of points, or coordinates carrying units that are not lengths.

`gradient(pos, *quantities)` returns one `(n, 3)` array per quantity in units of that quantity per metre. `divergence(pos, keys)` returns `(n,)` and `curl(pos, keys)` returns `(n, 3)`, both in units of the field per metre, where `keys` names the three components of a vector field. Wherever a method below takes a `keys` argument it means the same thing: the three components of a vector field in the order of the grid axes. A `keys` argument that does not name exactly three quantities, or whose quantities do not all carry the same unit, raises `ValueError`; units that are merely convertible to one another, such as volts per metre and millivolts per metre, are not the same unit.

`line_integral(vertices, *quantities)` integrates each quantity with respect to arc length along the polyline through `vertices`, and `circulation(vertices, keys)` integrates a vector field along that polyline following the direction it is travelled. Both need at least two vertices and raise `ValueError` otherwise.

`surface_flux(corner0, corner1, keys)` gives the flux through the axis-aligned rectangle with those opposite corners, taken towards increasing values of the one coordinate the corners share; corners sharing any other number of coordinates raise `ValueError`. `net_flux(corner0, corner1, keys)` gives the outward flux through the whole surface of the axis-aligned box with those opposite corners. `box_integral(corner0, corner1, *quantities)` integrates each quantity over that box, `volume_integral(*quantities)` integrates over the whole grid, and `box_mean(corner0, corner1, *quantities)` gives the average over the box instead of the integral. Wherever a path, a rectangle or a box reaches past the edge of the grid only the part on the grid counts, so an average is taken over the overlap alone and is not-a-number wherever that overlap has no volume.

`deposit(pos, amounts)` goes the other way, spreading each amount over the eight grid points around its position in the same proportions the field uses to weight those points, and returning an array shaped like the grid in the units of the amounts. Nothing is created or lost, so the total sitting on the grid is the total carried by the positions that lie on it, and a position off the grid deposits nothing. A count of amounts that does not match the count of positions raises `ValueError`.

`remap(target, *quantities)` returns a new `CartesianGrid` on the axes of `target` carrying each quantity, where the value at a target grid point is the average of the source field over the box centred on that point reaching half of the local target spacing in every direction, and a point whose box misses the source entirely is not-a-number.
