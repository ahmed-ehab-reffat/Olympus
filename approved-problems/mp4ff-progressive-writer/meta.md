# Build progressive MP4 files from fragmented input

Add `func (f *File) ToProgressive(cfg ProgressiveConfig) (*File, error)` with `type ProgressiveConfig struct { ChunkDurationMS uint32; LargeOffsets bool }`. It returns a new file whose children are ftyp, moov and one mdat, no longer reporting itself as fragmented. The input must be left untouched and share nothing with the result, so a later change to one never shows up in the other. Return an error for a file that is not fragmented, an init segment not describing the tracks its fragments carry, with no ftyp or mvex or a track without trex, and a fragment with no moof or mdat box, that names a sample description the init segment does not hold, that has no senc for samples carrying their own initialization vectors, or whose sample or encryption data does not fit it.

The ftyp comes from the init segment unchanged, and the moov without its mvex box, with every track's sample tables filled in. Everything else the moov holds is kept unchanged. Samples keep their segment, fragment and trun order, and the sample description they were written with, taken from the fragment or else from trex. An stsc run continues only while both the sample count and the description hold.

A chunk never spans a source fragment. A zero `ChunkDurationMS` gives one chunk per fragment; otherwise a chunk closes before the sample that would push its accumulated duration past that many milliseconds; every chunk holds at least one sample. Chunks are stored in mdat by ascending decode time of their first sample, compared in movie timescale, ties by ascending track ID; chunk offsets are absolute file offsets. `LargeOffsets` selects co64, a 64 bit mdat header and saio version 1; without it stco and saio version 0.

stts, ctts and stsc use the fewest entries that describe the samples. stsz uses the uniform size when all samples are equally big. ctts is written only when some composition offset is non-zero, and uses version 1 when some offset is negative and version 0 otherwise. stss is written only when not every sample is a sync sample, and holds one based sample numbers. sdtp is written only when some sample carries dependency information, and then holds one entry per sample, each packing the four dependency fields of that sample's flags.

The media duration sums the sample durations. A track duration is its media duration plus any leading empty edit, the sum in movie timescale, rounded down, and the movie duration is the longest of them. A track whose first sample starts late gets an edit list with a leading empty edit of that length followed by an edit covering the media; other tracks get none. Tracks without samples are kept with empty tables.

Encrypted tracks keep their per sample auxiliary information in the fragment layout, the initialization vector followed by any subsample ranges, written into mdat directly before its chunk's sample data, sized by saiz and located by one saio offset per chunk.
