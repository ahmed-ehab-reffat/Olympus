Title: Apply corrections and produce refused and undo files

ACH files can carry Notifications of Change, but File cannot apply them. Add CorrectionResult with Refused and Undo *File fields and add ApplyCorrections(corrections ...*File) (*CorrectionResult, error) to ach.File. Process files and their ordinary entries in argument and entry order, mutating the receiver in place. Only EntryDetail records in ordinary input batches can be notifications; IATBatches cannot. Return nil when there is no notification; otherwise return a result whose empty outputs are nil.

A notification identifies a receiver entry by OriginalTrace and OriginalDFI. Match both call-start values, even after an earlier routing change. Targets may be ordinary or IAT entries. C01 through C07 and C09 replace only their selected account, routing, name, transaction, or identification fields; routing includes its check digit. IAT supports only C02 or C08 routing, C05 transaction code, and C09 Addenda15 ReceiverIDNumber.

Continue after each acceptance or refusal; refusal is not an error. The first failed check sets RefusedChangeCode: unreadable data or a code without a supported forward field, C65; no OriginalDFI population, C61; no OriginalTrace in that population, C62; ordinary target named OFFSET, C62; code unsupported by the target representation, C65; unacceptable routing, C67; transaction code failing the concrete target batch's transaction, amount, or addenda rules, C69; then an ordinary offset left with nothing to balance, C69.

Offset feasibility sees earlier acceptances. Afterwards, preserved credit offsets equal non-offset debits and debit offsets equal non-offset credits. Keep offset codes and never add or remove an offset.

Refused contains one COR batch per input file with refusals, in argument order. Its file header comes from the receiver, and each batch header comes from the batch containing that file's first refusal. In refusal order, copy each notification entry and replace Addenda98 with Addenda98Refused carrying the refusal code plus the notification's change code, trace, DFI, and corrected data. OriginalTraceField() must return the original trace; TraceSequenceNumber is the notification trace's final seven digits.

Undo copies the receiver file header and uses one COR batch headed from the batch containing the last acceptance. Copy accepted notification entries in reverse acceptance order; set zero amount, NOC category, and addenda indicator one; regenerate ascending entry and Addenda98 traces from that batch's ODFI. Each Addenda98 keeps its change code, identifies the target by call-start trace and final post-call DFI, and canonically encodes the selected target fields from immediately before that acceptance. Applying Undo in one later ApplyCorrections call must refuse nothing and restore ordinary and IAT target fields, offsets, hashes, dollar totals, and counts. That call's Undo must reapply without refusal and reproduce the post-forward state.

Build batch and file counts, hashes, dollar totals, and service-class controls for both outputs. Rebuild receiver controls after offsets, including changed IAT batches. Use CreditsOnly for only credits, DebitsOnly for only debits, and MixedDebitsAndCredits for both; preserve an existing mixed class. Do not change correction inputs or add notifications to the receiver. Accepted no-ops have undo entries. Supplying no files is a no-op.
