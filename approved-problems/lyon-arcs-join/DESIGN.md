# DESIGN.md — lyon-arcs-join

## 1. Title
Add an arcs line join to the stroke tessellator

## 2. Shape classification
- Shape: O-Composite-add (new capability spanning parser-adjacent enum + tessellator geometry, cross-crate)
- Definition: new public enum variant (lyon_path) whose geometry is generated by deep modification of existing dense tessellator code (lyon_tessellation), not a standalone module.
- Pass rate target: <=40% ceiling (current sprint), aiming toward the hard end given S2+S3 stacked traps.
- Best agent: Vega (heavy multi-stage refactoring across real production code) or Orion (decisive commit-and-implement on a named-variant addition).
- Dominant verdict: WRONG_LOGIC (silent geometry error, since most integration sites are `if`/`==` not exhaustive `match`) + MISSED_REQUIREMENT (forgetting the zero-length-cap site or the fallback composition).
- Solver/our LOC ratio: unknown (no precedent for this exact shape); estimate ~1.5-2x given dense existing-code navigation overhead.

## 3. Public API surface
- `LineJoin::Arcs` — new enum variant on the existing `LineJoin` enum (crates/path/src/lib.rs), alongside Miter/MiterClip/Round/Bevel.
No other new public symbols; this is a pure enum-variant-plus-geometry addition, consistent with how Round/Bevel/MiterClip were each added historically (confirmed via `gh pr list` — PR #93 round, #158 bevel, #192 miter_limit — each added exactly one variant + geometry, no other API surface).

## 4. Canonical output form
- Curvature source: the circumscribed circle through the three points (previous edge's far endpoint is NOT used; only `prev.position`, `join.position`, `next.position` — i.e. the join point and its two immediate neighbors on the stroke centerline).
- Fallback trigger (union of two independently documented conditions): (a) the three points are collinear within a small tolerance (no finite circumradius), OR (b) the join distance from the plain miter position exceeds `miter_limit` times the half width (the SAME threshold semantics `Miter` already uses).
- Fallback target: `Bevel` geometry (not Round) — Bevel is the "cheap and always valid" join, matching the SVG2 note that arc joins degenerate to a plain corner when curvature information is unusable.
- Zero-length subpath cap: `Arcs` aliases to `Round` (curve-continuing family), not `Square`, at the existing cap-from-join-type fallback site.

## 5. Blind-spot pre-empts
- Unstated inverse: meta.md must state BOTH triggers for the fallback (collinear AND miter-limit-exceeded) as a single joined condition, not just one, since agents anchor to whichever is mentioned first (AGENTS.md "unstated inverse" blind spot).
- Default ordering: meta.md must not imply a NEW single threshold; explicitly says "the SAME miter_limit threshold used for Miter" to force reuse rather than a fresh invented number.

## 6. Description draft (meta.md)
~180 words, WHAT not HOW, no algorithm/site names. Draft:

"lyon's stroke tessellator supports Miter, MiterClip, Round, and Bevel joins but has no way to keep a stroke's curvature continuous through a corner the way SVG2's arcs join does. Add an `Arcs` variant to `LineJoin` whose join surface follows the circular arc implied by the join point and its two neighboring stroke points, rather than a straight offset or a fixed-radius circle.

When the join point and its two neighbors are collinear, or when the resulting join would reach farther than `miter_limit` times the half stroke width from the join point (the same threshold `Miter` already respects), the join falls back to a plain `Bevel` corner instead.

A subpath whose points all coincide already substitutes `Round`'s full-disc treatment for the cap when the line join is `Round`; `Arcs` should receive the same substitution, not the square fallback used by other joins."

## 8. Solution outline — pure-function helpers
- `circumcircle(a: Point, b: Point, c: Point) -> Option<(Point, f32)>` <- curvature source (returns None when near-collinear)
- `arcs_join_position(prev, join, next, half_width, miter_limit) -> Option<Point>` <- the extrapolated-arc intersection, None triggers bevel fallback <- composes circumcircle + miter_limit reuse
- Existing `join()`-area dispatch functions modified in place (not new files) per repo convention (Round/Bevel/MiterClip all live inline in the existing dispatch, no separate module per join type).

  - "arcs produces a smoother join than bevel, tighter than round-at-large-radius" (area ordering: bevel < arcs <= round for a shallow turn, comparable inequality math to prior miter/round/bevel ordering tests)

  - "sharp turn beyond miter_limit falls back to bevel" (degenerate trigger b, reusing miter_limit semantics)
  - "arcs is not silently treated as miter or round" (differentiation test against BOTH neighbors, not just one)
  - "zero-length subpath with Arcs caps as a full disc, not a square" (zero-length cap aliasing)
  - "closed subpath arcs join has no caps, interior still empty" (annulus-style regression coverage, mirrors existing closed-subpath tests elsewhere in the crate)
  - "existing Miter/MiterClip/Round/Bevel unaffected" (S3 baseline-preservation direct test, since silent regressions here are exactly the misdirecting risk)

| 5 | ORACLE-RESISTANCE: literally templating `tessellate_round_join`'s subdivision-count formula (`num_segments.log2().round()`, no floor) onto the two independently-computed sub-spans either side of the curvature peak | S-tier (oracle-defeating) — Round's own formula is provably insufficient once a single sweep is split into two data-dependent sub-sweeps | Round only ever has ONE span (full turn), so `log2(1)=0` is correct/intended there. Note: the original design's "zero-length cap site" trap (A8 polarity) was DROPPED during implementation — the actual zero-length-subpath cap dispatch reads `options.start_cap` directly with no reference to `LineJoin` at all, so there was never a real integration site there. Replaced with a benign no-panic smoke test (`arcs_join_zero_length_subpath_does_not_panic`) instead of a false trap claim.

CONTRACT-STATED/FIX-HIDDEN check: meta.md states the CURVATURE SOURCE (3 points), the FALLBACK CONDITIONS (both), the fixed/variable-width uniformity, and the 3 predictor functions' contracts (side selection, convexity, polyline shape) — none of these reveal the actual arc-intersection MATH (circumcircle formula, offset-radius derivation), WHICH functions/lines to touch, the internal `positive_side`/`front_normal` sign-convention plumbing, or the two-span subdivision-floor requirement. Fair.

**Post-authoring oracle-risk audit (2026-07-29):** `tessellate_round_join` sits in the same file and is a genuine template for "how do you tessellate a circular fan in this codebase" (angle bootstrap from side-offset points, winding-order swap for the negative side, recursive `tessellate_arc` subdivision). An agent could and likely would look at it. Audited what that reuse actually hands an agent vs. what it does NOT:
- **Handed for free (legitimate, not a difficulty source either way):** the general shape of "bootstrap two angles from side offsets, call `tessellate_arc` to fan between them."
- **NOT handed, and independently confirmed load-bearing by build-measurement:** the circumcircle-based curvature source itself (textbook geometry, but Round has no analog — Round's radius is always `half_width`, never derived from 3 points); the correct offset-radius sign determination (I got this wrong on first implementation — see feedback.md); the dual fallback trigger and its correct reuse of `miter_limit_is_exceeded` rather than a self-invented distance metric (also wrong on first implementation); the two-span subdivision floor (trap 5 above, directly disproven-as-templatable by mutation test); the multi-site wiring (trap 2); and the predictor/tessellator sign-consistency (trap 4).

Net: the oracle risk is real but partial — it removes only the "how do I draw a fan given two angles" sub-problem, which was never the hard part. The 5 traps above all survive templating Round because none of them has an analog in Round's own code.
