# Add event detection and backward integration to odefun

`odefun` integrates forward from its starting point only. Extend it so the object it returns can be evaluated at any `x` on either side of the starting point, and add `mpmath.ODEEvent(g, direction=0, terminal=False, reset=None, switch=None)` to describe a condition to watch while the solution is extended. A new `events` argument takes these objects, or plain callables that fall back on the defaults. Event functions, resets, switches and the callbacks below are all called the way `F` is, with a scalar state for a scalar problem and a list otherwise. The event function has to return a real value; anything else raises `ValueError`.

A crossing is a point where the event function vanishes and changes sign. Aim for working precision accuracy in event locations and in the derivative, search and integral queries below. A zero where a step starts, the starting point itself or an event just processed, is not a crossing. `direction` picks which crossings count: 1 keeps those where the event function increases through zero as `x` grows, -1 keeps the decreasing ones, and 0 keeps both. That sense always refers to increasing `x`, whichever way the solution is being extended. Any other value raises `ValueError`.

`sol.events` holds one list per event, in the order the events were given, each entry a pair of the crossing point and the state there, sorted by ascending `x`. The state recorded is the one arrived at, before any `reset` is applied, and `sol(x)`, `sol.diff(x)` and `sol.taylor(x, n)` all use that same arriving branch exactly at that point. Several crossings inside one step are taken in ascending `x`, and events falling at the same point are each recorded. Records appear as the solution is extended, so an unevaluated direction contributes nothing. `reset(x, y)` returns the state to carry on with. `switch` is itself the derivative function used for the rest of that direction, so it returns a derivative rather than another function. Both leave the other direction untouched.

`terminal` may be `True` to stop at the first crossing, or a positive whole number to stop at that many, counted separately in each direction; anything else raises `ValueError`. `sol.domain` is the pair of endpoints reached this way, using minus infinity and infinity where nothing stops the solution. Reading past a stop raises `ValueError`, and so does any method below asked for a point or range beyond one, while the stopping point stays available, including as the end of a range. `odefun(..., maxevents=n)` allows at most `n` crossings of one event in one direction and raises `ValueError` beyond that. `n` must be a positive whole number, and anything else raises `ValueError`.

The solution gains `sol.diff(x, n=1)` for the n-th derivative, shaped like `sol(x)`, where order zero returns the solution value and orders above the local series degree return zero, and `sol.taylor(x, n)` for the coefficients of the local expansion, one list per component or a single list for a scalar problem, where coefficient k is the k-th derivative over k factorial. `sol.integral(a, b)` integrates every component between two points, adding the two pieces when the range spans the starting point and `sol.integral(a, b, f)` integrates `f(x, y(x))` instead and returns one number, both staying accurate even when the integrand jumps at an event. Swapping the limits changes the sign and equal limits give zero. The order `n` given to `sol.diff` or `sol.taylor` must be a nonnegative whole number, and anything else raises `ValueError`.

`sol.crossings(level, a, b, index=0)` returns every `x` in the closed range where component `index` takes the given value, including where it only reaches that value and turns back without passing through, `sol.extrema(a, b, index=0)` returns every interior point where that component's derivative vanishes, both in ascending order, and `sol.maximum(a, b, index=0)` and `sol.minimum(a, b, index=0)` return the point and value where the component is largest or smallest over the range, endpoints included. The largest or smallest value can sit at an event, where the solution or its slope jumps, so those points are candidates too.

`sol.roots(g, a, b)` returns every `x` in the closed range where `g(x, y(x))` vanishes, in the same order, with `g` checked like an event function, so a value that is not real raises `ValueError`. A value touched without being crossed counts for these searches, unlike an event, so a level the component reaches and then retreats from is still a point where it takes that value. Each point is reported once, even where several lie close together. A value the solution reaches only at an event, because a `reset` moves it away at once, is still taken there and belongs in the result. Every one of these searches needs `b` above `a`, and where a component is named it has to exist, counting from zero, or `ValueError` is raised.

Add `odebvp(F, x0, y0, x1, y1, guess=None, stop=None, tol=None, degree=None, verbose=False)`, which solves a two point boundary problem. `y0` and `y1` list every component with `None` where the value is not prescribed, the number of unknown starting values must equal the number of conditions at the far end and at least one must be unknown, and `guess` supplies starting values for the unknowns and may be left out; a mismatch raises `ValueError`. Solve for the missing starting values so the far end conditions are met, and raise `ValueError` when no such values exist.

`x1` may lie before `x0`. With `stop` set to an event the conditions are read at its first crossing instead of at `x1`, which then only bounds the search and may itself be that crossing, and a crossing that never happens raises `ValueError`. That event is watched from the starting point like any other, so a value of zero there is not its crossing. The result is a solution object already carried out to the far end, and when `stop` is used that event is the one event the result carries, so its crossing is the first record in `sol.events`.
