## Design changes made during authoring

- `Transport` keeps its three public fields and the existing `increment_position` / `decrement_position` (the repo's transport tests build it as a struct literal and call them), and gains `*_crossfaded(…, crossfade_frames)` variants; the crossfade state lives in a `Crossfade` companion struct in `transport.rs`. The two old methods are `#[cfg(test)]` so the non-test build has no dead code. This keeps every existing repo test intact (no L31 cheat trap).
- Baked data keeps the same number of frames: only the last L frames of the loop are replaced and the loop region starts L later with the same end. First-pass output is then identical to the live crossfade, which the earlier "shorten the data by L" sketch would not have given. meta.md scopes the equivalence to forward play.
- Handle commands and seeks take effect a few frames after they are sent because the static resampler reads three frames ahead, and the tests assert the pattern once it settles rather than at an exact frame. A playing streaming sound keeps its buffered frames on any decoder-side command (upstream `discard_buffered_frames` returns early while advancing), so meta.md scopes streaming handle changes to "once the audio it has already buffered has played" (round 3).

## Fixture lessons

- Frame values (i+1)/16 made linear blends coincide with other source values (blend of frames 7 and 3 equals frame 5), so half the exact tests could not tell a blend from a replayed frame. Replaced by a 20-entry table over /256 searched for zero coincidences under every weight the tests use.
- The first pass of a crossfaded loop plays loop_start + L pure frames before the first blend; two prefixes were one frame long.
- A streaming decoder may be asked to seek twice in a row (start position, then loop head) with no decode between; an assertion demanding a decode in between was wrong.
