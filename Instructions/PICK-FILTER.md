# PICK-FILTER — pre-pick gates (run BEFORE authoring ANY Diamond/Olympus/Mars)

> **⭐ After the pick clears these gates, design the difficulty with `HARDENING.md`** — the survival-ranked trap arsenal (S/A/B + DEAD list) + CONTRACT-STATED/FIX-HIDDEN axiom. A pick whose only available traps are in the DEAD list is itself a dead pick.

Every gate below was paid for by a dead pick this session (2026-06-20). Run ALL at pick time. A candidate PASSES only if it clears every gate. Order: SOURCE (brainstorm) -> 10 GATES -> author. build-measure + reproduce-trap are NECESSARY-NOT-SUFFICIENT; the 10-run Nova/Orion (or Castor) BATCH is the ONLY difficulty oracle.

> **Pass-rate cap (admin 2026-07 sprint):** ONE TIER = Olympus, **≤40% pass** (Mars merged in; 0% = reject, >40% = too easy). Long-horizon floor: **≥250 eff LOC · ≥2 files · ≥40 solver-median msgs.** FP Check mandatory at the very end. Flakiness is a mandatory gate (Gate 9). This supersedes older ≤30%/≤20% figures — see `CLAUDE.md § RULE UPDATE 2026-07`.

> **Dead difficulty classes:** before scope-locking, check the candidate against `TOO-EASY.md` (Death-Class Taxonomy + shelved-sub case studies: membership/validation contract, single-subsystem mechanical transform, difficulty-from-misdirection, uniform-wrap, saturated-port). A candidate that matches a dead class is rejected here, not after three wasted batches.

## REPO-FIT (choose the REPO before the feature — community-confirmed 2026-07)

The best repos have **cross-cutting reach**: implementing ONE behavior correctly forces coordinated changes across multiple parts of the system, tied by a shared constraint/invariant so a change in one place forces a change elsewhere. Correctness depends on real rules/invariants where the OBVIOUS implementation is wrong (needs architectural understanding, not isolated edits). No coupling → not a good fit.

- **Size proxy: ≥ ~30k LOC in the target language.** A rough complexity floor — big enough to carry a substantial multi-stage change. NOT sufficient alone: a large repo can still be shallow. Always verify real cross-system architecture, not wide-but-flat surface.
- **Deterministic hidden-test surface (feature-level gate).** The cross-system feature must be assertable through deterministic INPUTS → OUTPUTS. If the interesting behavior can only be checked via snapshots, timing, network, concurrency, or visual inspection, it is a WEAK task even in a deep repo — drop it. (Ties to Gate 9 no-flaky-repo, applied at feature-pick time.)
- **Ruled-out repo classes (wide surface, little coupling):** CRUD/REST backends, admin panels, API glue = wide but uncoupled; UI / frontend component libs = visual, non-deterministic to test; scripts / CLIs / ETL = mostly IO wiring. Also avoid where the interesting behavior depends on private internals, network, concurrency, timing, vendored/generated code, or config — or the codebase is too small / too lightly factored to support a multi-stage change.
- **⚠ Nuance (community, KSL/dhruv):** the category is NOT an instant drop — CRUD/CLI repos CAN work IF the repo has genuine architectural DEPTH behind the operations. What's dead is ENTIRELY-CRUD / pure-IO-wiring with no cross-system architecture (difficulty stays low). Judge on coupling + depth, not the label.
- **License: if the repo has MULTIPLE licenses, EVERY ONE must be in the allowed list.** One non-allowed license (even in a subdir/vendored component) = the whole repo is a reject. Check all of them before investing. (Allowed set: `OFFICIAL-RUBRIC.md` + `RULES.md § Repository Requirements`.) Plus the basics: ≥500 stars, ≥1 commit in 12 months.

## GOLDEN-LOC ESTIMATION + LONG-HORIZON PROOF (run on the finalist BEFORE building — community-hardened 2026-07)

**Judge by the MINIMAL golden an expert would write, not by how a naive solver would flail.** The platform grades against the golden and the PASSING agents; a task whose correct solution compresses is a small task no matter how big it looks.

- **Compresses vs irreducible breadth — the decisive LOC question:** is the core ONE elegant algorithm (type inference, a parser, a clever data structure, a single optimization pass, a famous transform — reuses/wires into an existing engine) → it COMPRESSES below the floor, reject; or N DISTINCT behavioral cases (node kinds / type pairs / message types / states / resource types, each needing its own real code, no single shortcut collapsing it) → robust breadth that holds its LOC. Ask: "can ANY shortcut — an existing engine, one core algorithm, a config table, a library call — collapse the golden below the floor?" If yes, reject. ("Wire feature X into existing engine Y" = ~glue; "does the repo already have the machinery?" = the same question as Gate 4.)
  - **⚠ Reconcile with the POINTWISE-DECOUPLED law:** breadth secures SCOPE (the LOC floor); it does NOT secure DIFFICULTY. N independent handlers with no shared constraint = brute-force passes (our pointwise-decoupled kill). You need BOTH: irreducible breadth for the floor AND coupling (below) for the band.
- **SKELETON PROBE (structured golden estimate, cheaper than a full slice):** have one agent write the solution SKELETON only — real file layout, real signatures, control-flow comments, NO bodies. It reports files touched, modules crossed, implied logic-LOC, distinct behaviors, cross-subsystem invariants, and the single biggest collapse-shortcut. Treat the LOC as a LOWER bound (skeletons under-count). Borderline (within ~20% of a bar) → implement 1-2 representative subsystems to calibrate logic-per-signature, then re-judge. This kills the "looked big, built small" trap before authoring.
- **ULTRA-LONG-HORIZON = three load-bearing properties; write ONE proof sentence each or reject:**
  1. **SEQUENTIAL DEPENDENCY** — later work genuinely depends on earlier (data model before serializer before eval path); can't be parallelized or guessed out of order. Name the forced ordering.
  2. **WIDE BLAST RADIUS** — a partial/locally-correct solution still fails many tests because behaviors interact; no "do 30%, pass 30%." Name the interacting behaviors.
  3. **CROSS-SYSTEM INVARIANTS** — correctness is an invariant SPANNING subsystems (set in A, round-trips through B, honored by C, survives D's export). Name the invariant + the ≥2 subsystems.
  A big pile of independent functions with a big LOC number is NOT long-horizon. If you can't write the three sentences naming real subsystems/behaviors/invariants, reject. (This IS our globally-coupled law, operationalized.)
- **Kill-switch questions — ANY "yes" = reject on sight:** (1) could a strong engineer finish it in one afternoon? (2) could a competent dev start WRITING the solution within 5 minutes of reading the issue (path too obvious — a real task forces exploration of internals first)? (3) does it reduce to ONE elegant algorithm or ONE self-contained module behind light wiring?
- **Quick selection disqualifiers:** issue labeled `good first issue`/`beginner`/`easy` (check labels) = auto-reject; issue so old the codebase evolved around it (golden fights current architecture); Dockerfile unreasonably fragile to build offline; area has known-flaky tests (Gate 9).
- **API-heavy subsystem = reject-leaning shape (SELECTION-level, not just wording):** if the contract can only be pinned as a spec sheet of names/signatures/valid-value tables, the DESCRIPTION cannot be behavioral (P6 tension) — pick a different task. Favor semantic engines (evaluators, state machines, type/aggregation/protocol semantics, format round-trips) whose contract states as BEHAVIOR. A tiny forced API (single `Decode`, extend-existing) is fine woven into prose; a greenfield signature-table API is not.
- **High-collision textbook algorithms (derivative magnets — reject at selection):** phylogenetic likelihood/parsimony, Gaussian/Student-t processes, PCA/LDA variants, k-means/k-modes, vesselness filters, standard wavelet/FFT transforms, classic clustering/graph embeddings, common ML estimators. Many authors independently pick the same famous algorithm; surface differences read as cosmetic → derivative (~0.8) rejects. Favor "make THIS engine do X correctly" (repo-specific system engineering) over "implement famous algorithm Y."
- **Bars are PER-ASSIGNMENT — the platform's Submission criteria panel is the oracle** (per `OFFICIAL-RUBRIC.md`). Community numbers differ (some assignments run 500-1100 true-logic bands with ≥4 files; our current sprint floor is 250/≥2). Read the panel for YOUR assignment. **If the panel shows a band with a CAP and the honest golden overshoots it: CARVE to a coherent under-cap subset by dropping WHOLE behaviors — never pad, never thin the remaining behaviors; reject if it can't be carved without losing coherence.**

## THE 10 GATES

1. **BEHAVIORAL-F2P-GAP (the FIRST + decisive gate).** Base must produce OBSERVABLY WRONG output. The correct output must NOT be already-computed / composable from existing primitives / perf-only. RED: "naive composition already gives the right answer, this just makes it faster/cleaner." (KILLED diff-dataflow #80 = inequality-join composable from map+join+filter = perf-only; cue-disjunction = already-correct evaluator + "report WHY" = wrap.)
2. **SATURATION.** Not a faithful port/reimpl of a training-saturated reference (java.time, stdlib, Box2D, SVGO, any popular spec every model trained on). Survives only if the canonical is NOT in training OR the repo-integration non-obviously diverges. (KILLED js-joda, planck, oxvg.)
3. **UNIFORM-WRAP.** Difficulty must NOT be a single mechanism / one guard / one chokepoint-fix that discharges all walls (-> Nova ~100% once spec is fair, EVEN with a reproduced trap). Need MULTIPLE OPPOSING interdependent traps (fix-one-genuinely-regresses-another). (KILLED cel-exhaustive Nova 10/10, loro move-range fake-trap.) Memory: `lesson_uniform_wrap_dead_diamond`.
4. **LOC-CEILING.** Estimate the ACTUAL implemented fix-LOC (a real slice), NOT file/surface sizes. A fix to ALREADY-MOSTLY-CORRECT code = surgical ~30-50 LOC = sub-floor every tier. Durable = a genuinely-LARGE MISSING CORE (new operator/algorithm/capability). RED: "core ~80 eff -> bundle additive API to reach 450" (additive surface gets discounted as extensions). (KILLED yaegi value-bridge 36 LOC; flagged cue ~80 core.) Memory: `lesson_loc_ceiling_and_dedup_dir_scope`.
5. **COLD-NOT-LIVE (Section-9 by DATES).** The code path must be COLD — check commit DATES + release notes, NOT just "issue OPEN." Reject live maintainer workstreams + features being shipped now. (KILLED jedi #2025 ~60% shipped, OPA #557/#356 in-flight, risor match-churn.)
   - ⭐⭐⭐ **"COLD" MEANS THE CAPABILITY, NOT THE FILE — calibrated against the approved set 2026-08-04.** File-level commit velocity is NOT a reject criterion and using it as one over-rejects badly. **Measured on ACCEPTED problems:** `neva-array-bypass-generalization` touched `analyzer/network.go` (**33** commits in the 12mo before base), `desugarer/network.go` (**34**) and `irgen/network.go` (**15**), in a repo doing **600 commits/12mo** — and it was accepted. `pulldown-cmark-gfm-autolinks` touched `parse.rs` (100+ commits) and `lib.rs` (**52**). By a velocity rule those are all "hot". Note every kill example in this gate is a CAPABILITY collision (a feature ~60% shipped, a feature in flight), never file churn.
   - **The gate to apply:** is anyone — maintainer commit, merged PR, or open/draft PR — building THE CAPABILITY you intend to add? Overlay capabilities, not file lists. A busy file whose capability space is untouched is fine; a cold file whose capability just shipped is dead.
   - **Approved-set profile for reference:** 607-2666 stars, 0-17 open PRs, 33-600 commits/12mo, picks spanning 2-7 files across 2-4 subsystems, in deep multi-stage engines in unusual domains (HDL compiler, markdown parser, 2D tessellator, dataflow language, ISA assembler).
6. **REPRODUCE-ON-BASE.** For any bug-fix pick: CLONE + run the issue's exact repro through the REAL entrypoint (CLI/public API, NOT a caching test harness) + confirm it FAILS on base. OPEN issue != unfixed (a fix can land as a commit without closing). (KILLED loro-742 shipped, starlark-#139 fixed-commit e182421b.)
7. **DEDUP — ALL DIRS BY FEATURE CLASS.** grep diamond-problems/ problems/ Olympus-Approved/ (ALL, incl problems/<repo>/ subdirs) by FEATURE CLASS, not just the approved-Diamond dir. Read the JUDGE verdict (Duplicate-block / Derivative-near-reject / Adjacent-clears / Clear), NOT the raw scalar. (KILLED yaegi-reflect-identity missed in problems/yaegi/; expr-switch cleared as Adjacent.) Memory: `lesson_dedup_authored_set_and_lang_feature_cluster`.
7b. **★ EXCLUSIVITY — CANONICAL-ORG PR-DIFF (see CLAUDE.md § HARD RULE Exclusivity).** A public PR implementing your CENTRAL capability in ANY state (open/draft/unmerged/incomplete/closed) at ANY time = HARD scope-gate reject (binary, not contestable on quality). (a) Resolve canonical org FIRST — `CANON=$(gh api repos/OWNER/REPO -q '.full_name')` — repos MOVE, an -R old-org search returns EMPTY. (b) `gh pr list -R "$CANON" --state all --search "<feature CLASS>"`. (c) For every hit READ THE DIFF (`gh pr view <N> --json files`), NOT the body — "author says it doesn't work" routinely means the TESTS didn't exercise it while the CODE PATH is fully present. If the hit's changed-file set overlaps your core-machinery files -> EXCLUSIVITY-DEAD, shelve at PICK time. (KILLED nickel-optional-record-type: draft PR #2185 under the MOVED org nickel-lang/nickel touched my exact subtyping/pattern/mod/operation files; a full authoring + 4-batch cycle wasted. Same class: async-graphql, rhai, rune, gql-row.) Memory: `lesson_platform_similarity_blind_spot`.
8. **DEFINED-BEHAVIOR / MAINTAINER-PHILOSOPHY.** Behavior must be DEFINED by external-spec / sibling-template / maintainer-stated, NOT NeedsDesign / NOT_PLANNED / declined. (KILLED OPA #3478 NOT_PLANNED, dasel-multi-file declined.)
9. **★ NO-FLAKY-REPO (MANDATORY check, admin 2026).** The target repo's existing test suite must be deterministic. At pick time, clone + run the suite (or the blast-radius packages) 2-3x. If existing tests pass/fail nondeterministically (timing, ordering, network, resource contention, parallelism), either you can cleanly exclude those specific tests in `test.sh` base mode with a documented reason, OR the flakiness is pervasive -> pick a different repo. A repo whose baseline you can't make green-stable across runs is a dead pick. Your own new tests must also be 100% deterministic (see `TESTS.md § Flakiness gate`).
10. **★ REPO-QUOTA (per-repo submission caps, admin 2026).** Hard limits per repo: **≤6 submissions per repo (total, ours), ≤3 per repo in a single week, global ≤50 per repo across the whole quest** (ALL authors combined). The platform WARNS at submit time when any is surpassed — do NOT burn authoring effort on a repo you cannot submit against. **FIRST check `SATURATED-REPOS.md`** (maintained blocklist: Section A = platform-flagged over-used repos e.g. opa; Section B = our-own-cap-reached). ⭐⭐ **The GLOBAL cap is the trap: your LOCAL dir count is NOT the global count.** A repo can show 1 sub in our dirs yet be at 60 globally (opa: built + fully validated an Olympus sub, THEN the platform flagged opa "heavily over-used, 60 submissions" = over the 50 global cap = unsubmittable = a full build wasted, 2026-07-01). **POPULAR / HIGH-STAR repos saturate globally FIRST** — opa 11.9k★, and every author reaches for the well-known names. At pick time: COUNT our subs across ALL dirs (`Olympus-Approved/Feature-Requests/<repo>/`, `problems/`, `diamond-problems/`, `rejected/`), AND treat any well-known high-star repo (>5k★, or a household name in its niche) as PRESUMED-SATURATED globally — prefer genuinely NICHE repos (500-3k★, obscure) where the global count has headroom. **Star ceiling relaxed to 10000 on 2026-08-04 (user decision).** That widens what may be HUNTED; it does not weaken this gate. 5000-10000★ is a PENALTY band: admissible only when the repo's capabilities are repo-internal (not spec-named), and the platform sub-count must be checked on the "Learn more" page BEFORE authoring, since high-star repos saturate globally first. If the repo is at/over 6 ours, over 3 this week, or a popular high-star name, pick a DIFFERENT repo. **Already at/over cap (do NOT add more): opa (60 GLOBAL — DEAD), dasel (9), cliffy (7), yaegi (7).** Near cap (headroom in parens): expr (1), pest (1), katex (4→2 left), knex (4→2 left). Prefer NEW niche repos with full headroom for hard Olympus/Diamond picks.

**PASS PROFILE:** a bug-flavored CORRECTNESS GAP in COLD algorithmic code with externally-DEFINED behavior, in a repo with a DETERMINISTIC test baseline (base gives a wrong answer; the right answer is defined by a spec/sibling; the path is cold; a naive fix regresses something; existing tests are stable across runs). e.g. OPA #8302.

## SCOPE-INVENT LEVERS (when under LOC floor OR too-easy — INVENT, don't pad)

"Increase scope" = INVENT new genuine surface, NOT pad. Concrete levers:
- Add a public API method the feature lacks: `.Clone()` / `.Validate()` / `.String()` / `.Merge()`.
- Add a CO-EQUAL behavioral AXIS — a 2nd independent capability sharing state (expr-switch error-pillar; cel R9 dual-channel error-report). Also moves dedup Derivative->Adjacent.
- Cross-package/cross-subsystem integration with its OWN logic (CLI flag wiring, registry init, a consumer crate — T1 broadened wit-parser -> wit-component).
- Maintainer-blessed extensions (expr-switch: ranges / guards / exhaustiveness / multi-value / computed-dup — each a documented, fair lever).
- Additive READ-ONLY report/aggregation API over the structured output the solver already produces (StrictDynReport: +96 eff, zero solvability shift).

NEVER: dead code, duplicated logic, doc-comments (count ZERO for the LOC counter), or a LOC-pad-via-internal-module-tested utility (= Test-Fairness reject). Additive surface ALONE is discounted as "extensions" by dedup — pair it with a behavior CHANGE.

## META-DISCIPLINE

- reproduce-trap CONFIRMS a trap EXISTS, not that it RESISTS a strong agent.
- build-measure / surface-size CONFIRMS a surface, not the ACTUAL diff-LOC (implement a slice).
- The 10-run Nova/Orion/Castor BATCH is the ONLY difficulty oracle. If too-easy = single-mechanism, add an OPPOSING interdependent axis; if Nova clears it, PIVOT — don't iterate-to-force.
