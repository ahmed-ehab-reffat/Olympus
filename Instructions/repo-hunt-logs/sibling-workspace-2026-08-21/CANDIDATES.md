# Repository candidates

Last updated: 2026-08-20.

This registry is the active shortlist and decision history for repository
selection. Ratings are applicability scores from 1 through 10, not ordinal
ranks. Current facts have been refreshed through 2026-08-11. A repository is
not selectable until one concrete task clears the full saved-query, source,
history, Discussion, local-similarity, and cheapest-solution audit described
in `SEARCH_INSTRUCTIONS.md`.

Every investigated candidate is recorded here when it is rejected, including candidates that fail before a full prototype. A rejection entry states the repository, task seed, language, task type, decisive gate, and reconsideration condition so later searches do not repeat the same work.

### Offline environment eligibility

TypeScript and JavaScript candidates are ineligible unless the pinned upstream
revision commits a recognized dependency lock (`package-lock.json`,
`npm-shrinkwrap.json`, `pnpm-lock.yaml`, or `yarn.lock`) and declares every
build/test tool required after networking is disabled. Generating, embedding,
or downloading a replacement lock in the Dockerfile does not satisfy this gate.
A dependency-free exception requires explicit verification.

Before a problem folder is created, a pristine checkout must complete a minimal
official-base Docker build and run its intended build/test entry points with
networking disabled. A repeated build-context or image-creation timeout is a
terminal environment rejection, even when the proposed feature itself is
strong.

The supported implementation languages are Python, JavaScript, TypeScript, Go,
Rust, C++, and Java. A supported primary language does not hide an unsupported
core runtime: if meaningful compilation or tests require an unavailable
interpreter such as Ruby, the repository fails the environment gate until that
runtime becomes supported. Incidental native build dependencies remain
conditional on a successful pinned, offline image preflight.
