### The lane
**Capability (repo-model phrasing):**
- Every ProcessRecorder keeps a processing-step ledger. Each `insert_events(..., tracking=t)` call writes one row, including calls that record no events. The row holds the tracked leader name and notification id, plus the follower notification ids that step produced.
- A System-level consistent cut takes bounds on some applications' notification ids. For every application it computes the latest point in its own history where everything it had processed from each leader was within that leader's cut. When pipes form a loop, it iterates to the greatest fixed point.
- Three surfaces sit on top:
  - (i) cut positions per application, and processed positions per (follower, leader);
  - (ii) an aggregate or a notification-log slice read as of the cut;
  - (iii) forking a runner at the cut into fresh infrastructure (same ids, tracking and ledger), which then keeps running.

**Files:** persistence.py (ABCs), popo.py, sqlite.py, postgres.py (parity), system.py (solver, cut view, Runner fork), application.py (Repository read at a notification bound). That is 5-6 files across 3 subsystems.

### Gate 1, base gap
The probe `es_probe_cut.py` is deterministic under explicit `pull_and_process` and gave identical output 3x.
- **Setup:** leaders A and B; follower F follows both. Sequence: A:1 (no-op), A:2 -> F:1,2, B:1 (no-op), B:2 -> F:3, A:3 -> F:4.
- **What is recorded:** only `_max_tracking_ids == {'A': 3, 'B': 2}`.
- **What cannot be computed:** the cuts {A:2,B:2} and {A:3,B:1}. The second is subtle: A:3 is inside its bound, but it came after B:2 in F's history.
- **What is missing:** no cut, fork or as_of API exists, and `Repository.get` takes only `version`.

### Stage 6 death-class guard (run by me on RANK 1): PASS, with flagged risks
1. **One shared kernel feeding several surfaces?** Yes. One ledger plus one solver feed the positions, the cut reads and the fork. A local fix on one surface (e.g. the fork replaying by aggregate) diverges from the positions the solver reports.
2. **Interdependent traps?** Yes, pairwise as above. **Misdirecting?** Yes. Ledger granularity and no-op mistakes surface as wrong aggregate state or extra downstream events after a fork, not as ledger errors.
3. **Standalone new file with minimal wiring?** No.
   - The ledger must be written inside each backend's atomic insert (POPO `_update_table`, SQLite `_insert_events`) so that it survives reopening a file DB and stays consistent with tracking.
   - The fork must restore notification ids through the recorders.
   - Residual risk: an agent could record steps from `Application._record` via a side table. A test that reopens the SQLite file and asserts atomicity with tracking closes that route.
4. **TOO-EASY Pre-Pick Guard 1-5:**
   - #1: not one rule at N sites.
   - #2: spans persistence, application and system.
   - #3: the walls survive a meta that defines the cut exactly, because the fixes live in recorder internals the prompt does not name.
   - #4: "consistent cut" is nameable, but there is no repo-shaped implementation to crib.
   - #5: survives full spelling.
