### Base gaps, reproduced on base through the public API
A scratch test was written to the clone and deleted afterwards.

1. **Two-extreme padding is not a solve.**
   - What happens: `padX`/`padY` (`plot.go:257-369`) pick the single left-most and right-most box in the UNPADDED canvas. They then solve two linear equations for that pair only.
   - Reproduced: boxes (X=0, MinX=-50) and (X=0.3, MinX=-160) on a 400pt canvas give `DataCanvas` min X 55. The X=0.3 box then starts at **-1.5pt**, so it is clipped.
2. **Degenerate pair gives NaN.**
   - What happens: when the binding boxes share an X (or an oversized glyph sits at X=1), the solve divides by `lx - rx = 0`.
   - Reproduced: `DataCanvas` returned `{{-Inf 5} {NaN 300}}`. This is #773 ("plots fail to render"), with a nil error from Save.
3. **Align is not exact.**
   - What happens: Align (`align.go:20-119`) measures margins once on the initial tiles and then crops. Margins are a nonlinear function of the data size, because a box sits at bx*W + offset.
   - Reproduced: a 2x2 grid gave column 0 data Min.X 95.4810 vs 89.5002 and data widths 169.6921 vs 175.6729. This is #733, confirmed by sbinet as "interplay between DataCanvas and GlyphBoxer".
4. **Rotated and positioned labels.**
   - `horizontalAxis.size()`/`verticalAxis.size()` carry "We assume that the label isn't rotated" and use `Height(text)`.
   - The label glyph boxes for PosRight/PosTop carry `FIXME(sbinet): want data coordinates` (#722, #723).
   - The Legend is not a GlyphBoxer (#724).

### Lane and coupled surfaces
- **Lane:** glyph-aware exact layout. The data rectangle is the widest one that keeps EVERY glyph box inside the canvas: plotters, axis tick labels, axis labels and title. There is a defined tie-break and a defined overflow result. Save/WriterTo report the overflow as an error, which needs no API break. Align produces data canvases that are exactly equal in size and aligned per column and per row, by solving for the common data size against margins that depend on that size.
- **First shared operator:** every surface funnels through one margin model:
  - `Draw` (axes are drawn on `padX`/`padY` canvases);
  - `DataCanvas`;
  - `DrawGlyphBoxes`;
  - `Align` (which calls `DataCanvas` per tile);
  - Save/WriterTo.
- **Coupled surfaces:**
  1. the 1-D solver over all boxes, used twice;
  2. the padX/padY rewiring with the Plot.GlyphBoxes filters (Size<=0 per direction, X outside [0,1]) applied to plotter boxes but not to axis boxes;
  3. rotated axis label and title extents in size/draw/GlyphBoxes;
  4. PosRight/PosTop label boxes in data coordinates;
  5. the Align inverse (a common W/H in which each column's left/right margin and each row's bottom/top margin is a piecewise-linear function of W/H);
  6. the overflow result plus the error on Save/WriterTo;
  7. Legend boxes (#724) as an optional lever.
- **Missing machinery (named):**
  - an exact 2-variable LP per axis (maximise width subject to n + bx*w + minx >= cmin and n + bx*w + maxx <= cmax for every box);
  - its inverse for Align.

  The repo has only the two-extreme closed form and a forward-only Align.

### Stage 6 death-class guard (run on RANK 1)
1. **One shared kernel feeding several surfaces: YES.** The margin model feeds Draw (axes + data), DataCanvas, DrawGlyphBoxes, Align and Save/WriterTo. A local fix in padX that Align's margin estimate does not mirror leaves #733. Rotated extents change which box binds.
2. **Interdependent, not merely several: YES.**
   - The exact forward solve makes Align's one-shot margins wrong in a new way. Iterating DataCanvas converges only approximately, so the inverse must match the forward solve.
   - Rotated label sizes move the axis band and therefore the binding box.
   - The overflow rule must hold per tile inside Align.
   - The failing alignment assertion points at Align while the cause is the margin model (misdirecting).
3. **Standalone new file with minimal wiring: NO.** The solver can live in a helper, but it must be wired consistently through axis.go (sizes and unexported axis GlyphBoxes), plot.go (Draw, DataCanvas, the filters), align.go and the writer path. It is not a post-pass over a public stream.
4. **TOO-EASY Pre-Pick Guard:**
   - #1 (uniform-wrap): no.
   - #2 (single-subsystem fully-specified transform): no. It is a constraint solve plus its inverse, not inject/rewrite/reindex. Caveat: most of the diff sits in the root `plot` package, with `text` and the plotter producers as the second paths.
   - #3 (hardness needs the spec silent): no. The contract (no box outside the canvas, the widest data area, exact Align, defined overflow) can be stated in full and stays hard to derive.
   - #4 (port): no.
   - #5 (survives full spelling-out): yes.
