### The capability — "the parser lacks awareness of certain wiki-specific settings" (README, own words)

README `Limitations`, verbatim:

> Additionally, the parser lacks awareness of certain wiki-specific settings:
> * Word-ending links are not supported, since the linktrail rules are language-specific.
> * Localized namespace names aren't recognized, so file links (such as `[[File:...]]`) are treated
>   as regular wikilinks.
> * Anything that looks like an XML tag is treated as a tag, even if it is not a recognized tag name,
>   since the list of valid tags depends on loaded MediaWiki extensions.

Give the parser a per-parse site profile (linktrail pattern, namespace names + aliases with their
kind, recognised extension/HTML tag set) and make BOTH tokenizers, the builder and the Wikilink node
honour it: a trail attaches to the link it follows (never to file/category links, never across a
pipe-trick or style ticks), unknown tags become text (so an unclosed `<quetsch>` no longer swallows
the headings after it — the #311/#332 `get_sections` reports), and a link's namespace kind is
observable on the node. Shape **S-B + S-E** (missing domain effect threaded through every consumer;
generalisation over link forms).

**Base behaviour reproduced (Gate 1 / Gate 6, real entry point):**

```
'[[foo]]bar baz'         -> [Wikilink '[[foo]]', Text 'bar baz']
'[[File:x.png|thumb]]s'  -> [Wikilink '[[File:x.png|thumb]]', Text 's']
"[[foo|]]s ''it''"       -> [Wikilink '[[foo|]]', Text 's ', Tag "''it''"]
'<ref>a</ref>b'          -> [Tag '<ref>a</ref>', Text 'b']   (any <name> is a Tag)
```

### Stage 3b — machinery the repo LACKS (named)

- **No configuration reaches the tokenizers at all.** `CTokenizer.__init__` takes zero arguments
  (`tokenizer.c:99-103`, `kwlist = {NULL}`), `Parser.__init__` builds it bare, `definitions.c` is a
  static copy of `definitions.py` (comment: "should be kept up to date with definitions.py"). Tag
  recognition is three module-level predicates (`is_parsable`/`is_single`/`is_single_only`) called
  from `tokenizer.py:960-962,978,1335` and `tok_parse.c:1820-1871,2728`. A per-parser profile means
  new C state + marshalling + replacing static-table lookups in both implementations.
- **Nothing consumes text after `]]`.** `_handle_wikilink_end` (tokenizer.py:415) pops and returns;
  no token, builder branch or node attribute exists for a trail (`tokens.py`, `builder.py:153-166`,
  `nodes/wikilink.py`). The trail must be tokenised (both tokenizers), carried, built and rendered
  back by `__str__`/`__strip__` losslessly.
- **No namespace classification anywhere** (`grep -rn namespace src/` = 0 hits).

Nearest sibling for calibration: PR #81 "Implement MediaWiki table parsing" (2014) = +1357/-108 for
one tokenizer-level construct done in both tokenizers + builder + node. Sketch for this pick:
Python tokenizer ~110 · C tokenizer ~250 (dynamic tag sets, trail scan, init kwargs) · definitions
py+c ~60 · tokens/builder ~30 · Wikilink node ~50 · Parser/parse API + profile object ~60 ->
**~550 raw, ~380 effective** against a 200 floor. A thinnest end-to-end spike is owed before
scope-lock (`REPO-HUNT-2026-09-10-D` law), but this is new machinery, not a call-through.

### Gate 8 — maintainer philosophy: **YELLOW, mitigated — read before authoring**

- **#82 (2014-12)**, `earwig`: *"This would have to be an argument to `mwparserfromhell.parse`... I'm
  really uncomfortable about adding site-specific arguments like this to that function. Maybe we
  should consider the current behavior correct?"* Two contributors pushed back the same day ("the
  maintainability of the parser shouldn't be affected as long as it does not implement any
  site-specific logic"); earwig never replied, the issue is still OPEN.
- Counter-evidence: he then shipped `skip_style_tags` as a parse-time mode argument (CHANGELOG lines
  223 and 180, later releases), the README frames all three items as *limitations* the parser
  "lacks", **#305 (2023, 0 comments)** asks for exactly `Parser(recognized_tags=..., namespaces=...)`
  and was not declined, and the docs promise "multiple parsing modes" in a future version.
- **Mitigation for the author:** put the profile on a `Parser`/profile object rather than a pile of
  kwargs on `mwparserfromhell.parse()`; keep every rule data-driven (the profile carries the data,
  the parser carries no per-site logic) — that is precisely the split the 2014 objectors proposed.
  Record this thread in `meta.md`'s author notes; a reviewer running Pattern 22 will find it.

## Method notes

- **Six parallel GraphQL workers, not one.** 22.8k slugs in ~30 min. `pkill -f <script>` kills the
  tool shell when the pattern appears in your own command line; use `pgrep -f 'name[.]py'` in a call
  that does not otherwise mention the script.
- **Raw README fetch is free and the limitation grep works at index scale**, but it is noisy: most
  hits are docs caveats. Restrict to domain-engine slugs first (907 of 2452 here), then read only
  "not supported / not implemented / only supports / is ignored" lines.
- **The winning lane was a README `Limitations` section, again** (tippecanoe 09-12, mwparserfromhell
  today). Grep `Limitations|Caveats|Known issues` headings on every finalist before the tracker.
- **A sibling library's README is a free absorption + port check.** wikitextparser documents the
  same three gaps and cites mwparserfromhell's issue numbers — one curl settled Stage 3b's port
  question and confirmed the gap class is real in the whole ecosystem.
- **Read a philosophy hit against later behaviour.** The 2014 "uncomfortable" comment reads as a
  decline until you see the maintainer add a parse-time mode argument afterwards and leave the 2023
  config request undeclined. Record both sides; let the author phrase the API to the objection.
