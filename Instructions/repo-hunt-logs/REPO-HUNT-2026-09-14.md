### The capability — compose YAML schemas (S-B config-layer + S-A second entry point)

Issue **#1148 (OPEN, 2025-01)**, maintainer `msbarry`: *"There is not currently a way to combine 2
profiles in a single run. It would be pretty trivial to support combining the layer/feature
definitions from 2 or more profiles ... but I'm not exactly sure what the best way to merge other
properties like the source definitions?"* — welcomed, no design published, no PR (Phase 2 searches:
extends / inherit / include / combine / import / multiple schema / merge profiles -> only #1148).

Give a YAML schema an `extends` list of other schema files (paths relative to the declaring file),
resolved recursively with cycle detection, and merge the results into one `SchemaConfig` before the
existing pipeline (args fixpoint, `ConfiguredProfile`, `SchemaValidator`) sees it; and let the CLI
take several `--schema` files, composed the same way. Merge rules are the design space: sources by
id, `tag_mappings` and `definitions` as maps with child precedence, `args` merged so a child can
override a parent default while parent descriptions/types survive, layers by id (child layer with
the same id keeps the parent's POSITION, its features are appended, other fields child-wins), a way
to drop an inherited layer, `examples` concatenated and validated against the composed schema,
scalar root fields child-wins.

**Machinery the repo lacks (Stage 3b):** `SchemaConfig.load` is one `YAML.load` call into a flat
record; there is no loader with a file graph, no merge of any record, no path resolution beyond the
validator's `examples: <sibling file>` precedent (`SchemaValidator.java:59-66`), and
`ConfiguredMapMain` takes exactly one `--schema`. The args fixpoint (`Contexts.buildRootContext`,
iterates "until their values settle", `ParseException` after 100 iterations) exists and is the
F-22 seam: composed args must be settled TOGETHER, not per file.

Sketch: loader + graph + cycle/path handling ~120 · merge rules over 8 record types ~160 · CLI
multi-schema + validator watch paths ~50 · error types ~20 -> ~350 raw, ~250 effective. Above the
200 floor with a thin buffer; the thinnest end-to-end spike must be measured before scope-lock,
and a genuine second lever (e.g. layer removal + position rules as a stated polarity axis) is
already in the scope rather than bolted on.

### TRAP SEAMS

| Pattern | Present | Evidence |
|---|---|---|
| **F-22 joint fixed point** | yes | `Contexts.buildRootContext` settles args iteratively; parent defaults referencing child args (and vice versa) only resolve if the merged map is settled once |
| **F-25 placeholder / cycle** | yes | `extends` graph: self-extends, mutual, diamond (D reached via B and C must be included once, deterministic order) |
| **A8 ordering / position** | yes | composed layer order: parents first in document order, a same-id child layer keeps the parent's position; tile layer order is user-visible in the output |
| **F-9 cross-stage path resolution** | yes | relative `extends`, `examples` and `local_path` resolve against the DECLARING file, not the root file or the CWD; the validator already resolves `examples` via `resolveSibling` — the merged schema must not lose the origin |
| **F-10 cross-product** | yes | multiplicity (one parent / several / chained) x polarity (override vs. remove) x entry (file `extends` vs. CLI list) |
| **F-20 sibling API** | yes | single-file `SchemaConfig.load(path)` and `--schema one.yml` must behave byte-identically (existing `SchemaYAMLLoadTest` + samples guard it) |
| F-3 carve-out | yes | `definitions` is an unparsed anchor scratch-space (YAML anchors cannot cross files) vs. `tag_mappings` which must merge semantically |

**Phase-3 death-class guard:** one composition kernel feeds the args fixpoint, the profile, the
validator and two entry points; a per-file evaluation passes single-parent tests and breaks
cross-file args; position rules break the simple "concat layers" implementation. Not a standalone
file: `SchemaConfig`, `ConfiguredMapMain`, `SchemaValidator`, `Contexts` all change. Pre-Pick Guard:
not a single guard; not a pure mechanical transform once args/paths/positions interact; hardness
survives full statement; not a port (planetiler's own model).

**Honest difficulty read:** this is a config-merging feature and the merge rules are transcribable;
the band prediction is 30-45%, i.e. approvable under the 50% ceiling but not a low-pass pick. The
levers that keep it under the ceiling are the joint args fixpoint, the position rule, the
declaring-file path rule and the diamond/cycle cells. Under the PRIME DIRECTIVE it is a fallback
to a deeper pick, not the target — but it is the only lane that cleared every gate today.

### Derivative risk

MEDIUM. "Schema inheritance / extends" is a well-known config idiom (Helm, docker-compose, ESLint),
and 45 issues + 54 PRs mention YAML on this repo, so the lane is visible. Mitigations: phrase
`meta.md` entirely on planetiler nouns (`SchemaConfig`, sources, `tag_mappings`, `args` settling,
layers, `examples`, `SchemaValidator`), build the F-10 table, and run the platform precheck on the
thinnest slice BEFORE writing the cross-product cells (Step 4b).

### Risks

1. Lane is visited by two real outside contributors (`zstadler`, `phanecak-maptiler`) who add small
   custommap features every few months; re-run the PR-DIFF at submit.
2. The submodule: the platform checkout may lack it; the Dockerfile must fetch it (network at
   build) or the reactor cannot parse.
3. Base mode = the custommap module only (core tests are minutes long and untouched); document.
4. Effective LOC lands near 250; do not pad — if the spike is under 200, add the CLI multi-schema
   mode as the coupled second lever, not more merge rules.

## Method notes

- **Domain awesome-lists are the best of the four new indexes** (309 passing, one authorable);
  Debian is infra-heavy, code search is capped at 1000 hits per phrase and dominated by small
  repos, fresh topics are down to ~1 lead per 50 topics.
- **A Java multi-module reactor needs three things to run offline:** the submodule present, the
  `flatten` profile at install, and one online test run to fetch the Surefire provider. Write them
  into the Dockerfile in that order.
- **Read a maintainer's "pretty trivial" as an LOC warning, not as a design.** #1148's easy half
  (concatenate layers) is trivial; the pick lives in the half he called unclear (sources, args).
