**Best Olympus feature types:**

1. ⭐ **Lower `Positive`/`Negative` fill rules through every output backend.** The core winding
   engine defines four fill rules; six emitters collapse them to the SVG/PDF two-value binary, and
   **each collapses differently** (rasterizer flips to EvenOdd, pdf/ps/svg silently fall back to
   NonZero, htmlcanvas/tex ignore FillRule entirely). Since no output format can express
   Positive/Negative natively, the only correct fix pre-resolves path geometry through the winding
   engine into an equivalent NonZero path — so a "fix" in the emitter forces engagement with the
   boolean/winding core. Interdependent (a per-backend local map is wrong and observably so),
   misdirecting (failure surfaces as wrong emitted bytes/pixels, cause is winding semantics).
   **Critically: `Positive`/`Negative` are canvas's OWN model — no external spec names them — so the
   dedup one-liner cannot be written without repo-internal nouns. Stage 2b risk LOW.**
2. **Coordinate-system/view fidelity across Context ops and backends.** `CoordSystem` (4 quadrants),
   `SetCoordView`, `SetView`, `Push`/`Pop` (canvas.go:276-333). Open bugs #314 (`canvas.Clip`
   translation ignores coordSystem) and #348 (CoordView not scaling under rasterizer) are evidence
   of real behavioural gaps. Own model, not spec-named. Use as evidence, invent the scope.
3. **Line-breaker parity: `KnuthLinebreaker` vs `GreedyLinebreaker`** (text.go:409,617) behind one
   contract = S5 dual-path. Weaker: risks the DEAD "make X consistent with correct sibling Y" class.

### ✅ GATE 1 — BEHAVIORAL-F2P-GAP: **CONFIRMED** (run 2026-08-07 through the public API)

Probe: `canvas.MustParseSVGPath` -> `canvas.NewContext(<backend>)` -> `RenderPath` with
`Style.FillRule` set, one backend at a time. Ground truth taken from the core two ways:
`FillRule.Fills(windings)` and `Path.Settle(fillRule)`.

Core is CORRECT on all four rules: `Fills(+1/-1/+2)` = NonZero `t/t/t`, EvenOdd `t/t/f`,
Positive `t/f/t`, Negative `f/t/f`.

**Decisive case — clockwise square `M2 2 L2 18 L18 18 L18 2 z` (winding -1) with `FillRule=Positive`.
Core says paint NOTHING (`Settle(Positive)` is empty; `Positive.Fills(-1)==false`). Every backend
paints it:**

| Backend | emitted | correct? |
|---|---|---|
| PDF | `2 2 m 2 18 l 18 18 l 18 2 l f` (nonzero fill) | ✗ should paint nothing |
| SVG | `<path>` with NO `fill-rule` attr (defaults nonzero) | ✗ |
| PS | `fill` (nonzero) | ✗ |
| rasterizer | **256 inked pixels** (expected 0) | ✗ |

Symmetric failure: CCW square + `FillRule=Negative` — core empty, all four backends paint 256 px.

**The backends also disagree WITH EACH OTHER** — nested CW squares (inner winding -2) under
`Positive`: rasterizer inks **224 px** (the EvenOdd answer, via `SetWinding(fr == NonZero)`) while
SVG/PS/PDF emit the **NonZero** answer (324 px of geometry). Two different wrong answers from one
input, which is the interdependence demonstrated empirically rather than argued.

Correction worth carrying: a first pass reported PDF as also dropping `EvenOdd`. That was an
artifact of `pdf.Options.Compress` defaulting to true making the content stream unreadable. With
`Compress: false`, PDF emits `f*` for EvenOdd correctly. **The gap is exactly Positive/Negative, in
all of PDF, PS, SVG and rasterizer, plus htmlcanvas/tex which reference `FillRule` not at all.**
