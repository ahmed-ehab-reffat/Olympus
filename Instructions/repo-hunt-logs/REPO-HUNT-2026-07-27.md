## TIER 1 — best fits

### 1. googlefonts/fontations — 797★ · Rust · Apache-2.0 OR MIT
- URL: https://github.com/googlefonts/fontations · last commit 2026-07-23 · **199 open issues (no PRs)** ✓ in band
- **Domain:** OpenType/TrueType font compiler + reader. Crates: `font-types`, `read-fonts` (zero-copy table parsing), `write-fonts` (table compilation), `skrifa` (glyph outline/metrics/variation/color engine), `font-codegen` (table codegen from a DSL), `incremental-font-transfer`, `font-test-data`.
- **Architecture:** genuine 4-stage pipeline — codegen → table read → variation/instance resolution → outline/metric evaluation. Crate boundaries are hard, `read-fonts` and `write-fonts` must stay round-trip consistent.
- **Tests:** `#[test]` in-crate plus a dedicated `font-test-data` crate of real font binaries; behavioral assertions on parsed/produced tables and outlines. No mocking, offline fixtures.
- **Docker:** Pattern A (`olympus-base-rust` + chmod/symlink). Pure Rust, no system deps, offline-buildable.
- **Olympus feature types:** a missing OpenType table or subtable format threaded read→write→skrifa (COLRv1 paint graph corner, `MVAR`/`HVAR` delta application, `GDEF` variation store); variable-font instancing of an un-instanced table; hinting/metric resolution under variation coordinates; subsetting-adjacent capability across read+write.
- **Complexity:** 400-900 effective LOC realistically reachable — the read/write symmetry doubles every capability-add, which is exactly the "family of N related capabilities" the LOC law wants.
- **Why it matches:** deeply niche (font-binary internals are thin training data), spec-defined by OpenType (fair oracle), cold subsystems, three crates minimum per feature, very active but with a huge unimplemented surface.

### 2. nevalang/neva — 1076★ · Go · MIT
- URL: https://github.com/nevalang/neva · last commit 2026-07-26 · **108 open issues (no PRs)** ✓ in band
- **Domain:** dataflow programming language — `internal/compiler` (parser via ANTLR-generated Go, analyzer, desugarer, IR generator, Go backend) + `internal/runtime` (message-passing scheduler, connections, funcs).
- **Architecture:** parse → analyze (typesystem with subtyping/generics) → desugar → IR → backend → runtime. Five stages with distinct data structures; a new language construct must thread all of them.
- **Tests:** Go `testing` + testify unit tests per compiler stage, plus an `e2e/` directory of ~100 golden programs (each dir = source + expected stdout) run through the real compiler+runtime. Behavioral, public-entrypoint, no mocking — and programs are runtime strings, so new-syntax features give clean fail-to-pass on base.
- **Docker:** Pattern B (`olympus-base-go`), `go mod download`. Pure Go.
- **Olympus feature types:** a new connection form or port semantic (fan-in ordering, array-port holes, deferred connections) across desugarer→IR→runtime; typesystem gap (union narrowing, recursive generic resolution); a new stdlib component requiring runtime scheduler support; error-propagation construct.
- **Complexity:** 350-700 effective LOC; cross-stage wiring is genuinely new code, not reuse.
- **Why it matches:** the closest thing in the pool to bunster/cliffy — obscure to problem authors, real multi-stage compiler, in-band tracker, golden-file behavioral tests, and an explicitly incomplete language.

### 3. rust-minidump/rust-minidump — 505★ · Rust · MIT
- URL: https://github.com/rust-minidump/rust-minidump · last commit 2026-07-20 · 77 open issues (no PRs) — below band
- **Domain:** crash-dump forensics. Crates: `minidump` (stream parsing), `minidump-common`, `minidump-unwind` (CFI / frame-pointer / scan unwinders), `breakpad-symbols` (symbol file parser + supplier), `minidump-processor` (stack walking → JSON report), `minidump-synth` (synthetic dump builder for tests).
- **Architecture:** parse streams → resolve modules/symbols → unwind per-thread stacks → symbolize → report. Four crates per feature, and the unwinder is globally coupled (one bad frame corrupts the whole walk — the same "cascade" shape that made lyon/go-geom viable).
- **Tests:** `#[test]` using `minidump-synth` to construct dumps in-memory plus `testdata/` real dumps; assertions on walked frames and JSON report fields. Strong behavioral surface, zero mocking, fully offline.
- **Docker:** Pattern A. Pure Rust.
- **Olympus feature types:** a new unwinder strategy or architecture (ARM64 pointer auth, ranged CFI evaluation, inline-frame reconstruction from symbol data); DWARF/Breakpad `INLINE`/`INLINE_ORIGIN` records threaded symbols→unwind→report; a missing minidump stream surfaced end-to-end into the processor's report.
- **Complexity:** 300-600 effective LOC. Watch the floor — some stream additions are compact; build-measure a slice first.
- **Why it matches:** extremely niche domain, externally-defined formats (Breakpad/minidump specs = fair), cold code, 4-crate span, deterministic fixture tests. Star count sits just above the 500 floor.

### 4. 0xMiden/miden-vm — 760★ · Rust · MIT OR Apache-2.0
- URL: https://github.com/0xMiden/miden-vm · last commit 2026-07-25 · **124 open issues (no PRs)** ✓ in band
- **Domain:** STARK-based zero-knowledge VM. `crates/assembly-syntax` + `crates/assembly` (Miden Assembly → MAST), `core` (opcodes/decoder layout), `processor` (execution + advice provider + memory chiplets), `air` (constraint algebra), `prover`/`verifier`.
- **Architecture:** the strictest pipeline in this list — any new instruction must be defined in assembly syntax, lowered to MAST, executed in the processor, *and* constrained in the AIR. Execution and constraints are two evaluators of one semantics (HARDENING S6), so a partial implementation passes execution and fails proving.
- **Tests:** `#[test]` + `proptest` in `processor/tests` and per-crate; programs are assembly source strings executed through the public `Assembler`/`Process` API. Behavioral, offline.
- **Docker:** Pattern A. Pure Rust (large workspace — expect a slow first build; pre-fetch the cargo registry in the image).
- **Olympus feature types:** a new instruction or instruction family (field/u32 op, memory/word op) threaded assembly→MAST→processor→AIR; a decorator/advice-provider capability; control-flow construct (loop/call boundary) with its MAST digest and constraint implications.
- **Complexity:** 450-900 effective LOC; the four-layer requirement makes under-floor unlikely.
- **Why it matches:** the two-evaluator shape is the highest-value trap structure we have measured, the domain is deeply niche, and the ZK/proving layer is very thin training data. Caveat: 158 MB repo, heavy build.

### 5. lalrpop/lalrpop — 3495★ · Rust · Apache-2.0 OR MIT
- URL: https://github.com/lalrpop/lalrpop · last commit 2026-07-25 · **154 open issues (no PRs)** ✓ in band
- **Domain:** LR(1)/LALR parser generator. `lalrpop` (grammar parser → normalization passes → LR(1) table construction → lane-table conflict resolution → Rust codegen), `lalrpop-util` (runtime), `lalrpop-test` (integration grammars).
- **Architecture:** grammar AST → macro expansion/inlining/precedence normalization → first/follow → LR automaton → state machine or recursive-ascent codegen. Six normalization passes, each its own module.
- **Tests:** `#[test]` unit tests per pass plus `lalrpop-test`, which compiles real grammars in `build.rs` and asserts parse results. Behavioral through generated parsers.
- **Docker:** Pattern A. Pure Rust.
- **Olympus feature types:** a grammar-level construct (new repetition/optional-with-separator form, parameterized-macro extension) through normalization→table-build→codegen; improved conflict diagnostics from the lane table; error-recovery capability surfaced in the generated parser.
- **Complexity:** 400-700 effective LOC.
- **Why it matches:** closest domain sibling to our six approved `pest` problems — the shape is proven — while lalrpop's LR/lane-table machinery is a genuinely different and much colder subsystem. **Risk:** 3495★ sits at the top of your range, and the "parser generator" class is adjacent to a heavily mined family; run the derivative check hard before authoring.

## neva — best overall shape

- MIT, 52k Go LOC across `internal/compiler` (35.8k) + `internal/runtime` (16.4k), five real stages: parser → analyzer → desugarer → irgen → backend → runtime.
- Churn is concentrated in `runtime/funcs` (1032 file-touches/6mo) and stdlib/CLI — **avoid those**. The mid-compiler (typesystem 2.7k LOC with resolver/subtype-checker/recursion-terminator, desugarer, irgen) is cold at 3 commits/90d.

- **Zero open PRs** — the maintainer merges fast (most branches are `codex/...`, AI-assisted, and the repo has an explicit generative-AI policy). Exclusivity is easy to check but gaps can close mid-authoring: re-run the SIX-CHECK immediately before submit.
