### ⭐ Traps REPRODUCED ON BASE in this session (vitest, jsdom, no WebGL)

I installed the repo and ran probes against `61757db`. All four probes passed; these are measured
outputs, not code-reading.

1. **The lane is reachable headlessly.** `new Planet({name:'p'})` then
   `v._planet = planet; v._createEntityCollectionsTree(ents)` builds an
   `EarthEntityCollectionsTreeStrategy` with a populated tree. No renderer, no GL. (`Vector.addTo`
   itself does need `planet.renderer.handler` — `Vector.ts:400` — so a test must take the strategy
   route, exactly as the repo's own `tests/quadTree/EntityCollectionNode.test.js` already does.)
   **This was the pick's make-or-break risk and it is now closed.**
2. **`_nodePtr` is assigned ONLY on the split path, so `removeEntity` leaks the ancestor count.**
   `buildTree` sets `ei._nodePtr = cn[NW|NE|SW|SE]` only inside the `entities.length >
   _nodeCapacity` branch (`EntityCollectionNode.ts:139-148`); the `else` branch calls
   `_addEntitiesToCollection` and sets nothing. MEASURED: 3 entities with `nodeCapacity: 5` ->
   root children 0, root count 3, **`_nodePtr` set on 0 of 3**. After `v.removeEntity(ents[0])` the
   entity collection correctly holds 2 but **`root.count` stays 3, permanently**. Misdirecting,
   because `collectRenderCollectionsPASS2` gates on `count > 0`: the symptom is a rendering
   anomaly much later, and a correct count fix makes previously-visible collections disappear.
3. **`nodeCapacity` is honoured only at bulk-build time.** `insertEntity` calls `buildTree([entity])`
   and `1 > _nodeCapacity` is always false, so it appends to the existing leaf forever. MEASURED:
   8 entities at `nodeCapacity: 4`, then 60 `insertEntity` calls clustered in one quadrant ->
   **root count 68, root children still 4, leaf sizes still 3/1/3/1.** This is F-15 verbatim: an
   arming condition that never fires.
4. **An entity that moves never re-homes, and the two public setters disagree about the mercator
   coordinate.** MEASURED: 12 entities, `nodeCapacity: 3`; move one to `lat 88` (past
   `mercator.MAX_LAT = 85.05`) with `setLonLat` -> merc tree count stays 12, north tree stays 0.
   `Vector._bindEventsDefault` has the `entitymove` binding **commented out**, and
   `Entity.setCartesian` ends with a commented `//ec && ec.events.dispatch(ec.events.entitymove,
   this);`. Worse, `Entity.setLonLat:1188-1191` leaves `_lonLatMerc` **stale** past MAX_LAT (the
   line `//this._lonLatMerc = null;` is commented out) while its twin `setLonLat2:1217-1220`
   explicitly zeroes it — two spellings of one concept with divergent state (F-18), so a re-home
   hook wired through one API re-homes on a stale mercator coordinate through the other.

**The fourth interdependency, read from source:** `alignEntityToTheGround` calls
`entity._setCartesian3vSilent(...)` on every clamp-to-ground render pass, so the obvious
"notify on the cartesian setter" fix turns every frame into tree churn. The fix location is the
trap.

**Fifth, latent:** `buildTree` does `this.count += entities.length` and then silently drops any
entity matching none of the four children (boundary coordinate, or `_lonLatMerc` unset). MEASURED
adjacent behaviour: an entity whose `_lonLat` is left at (0,0) gets `_lonLatMerc = (0,0)`, so a
cluster of them recurses `buildTree` until the stack overflows.

### Stage 6 death-class guard — PASSED

1. **One shared kernel feeding several surfaces, where a local fix regresses another?** YES.
   `EntityCollectionNode` is consumed by three node classes with three different `isInside`
