### The capability — crossfaded loop regions

A loop region gains a crossfade length. Over the last L frames before the loop's end, the output
blends the frame at the playhead with the frame the same distance after the loop's start, linearly
from all-tail to all-head; when the playhead reaches the loop end it continues from loop start plus L,
because those head frames have already been heard. The rule holds for the static sound (frames in
memory), the streaming sound (frames arrive from a decoder thread through a ring buffer, so the head
frames must be fetched ahead of time without the decoder seeking away from the tail), reverse
playback (the fade sits after the loop start and the wrap lands on loop end minus L), non-unit
playback rate (the fade is measured in source frames, blended before resampling), seeking into or out
of the fade window, and a loop region or fade changed while playing through the command channel.
Fade longer than the loop, fade with an `EndOfAudio` loop end, and a fade on a sound without a loop
region need stated canonical answers. Settings builders for both sound types, both handles, the
command readers, `Transport`, both `process` loops and the decode scheduler change.

**Machinery the repo lacks (Stage 3b):** no second read position anywhere (static reads one index
through a 4-frame resampler window; streaming has one decoder cursor and one ring buffer), no
frame-blending outside per-parameter volume tweens, no transport notion of a fade window, no
scheduler pre-fetch of a non-contiguous range. The `PlaybackStateManager` fade tween is a VOLUME
envelope on one stream, not a crossfade between two positions, so it is not an oracle for the
mechanism. Sketch: transport arithmetic ~50 · static blend + second window ~90 · streaming scheduler
pre-fetch + blend ~170 · settings/handles/commands x2 ~70 · canonical edge rules ~30 -> ~410 raw,
**~300 effective**, 10-12 files.

**Phase-3 death-class guard.** (1) One kernel (transport wrap target + blend window) feeds two
playback paths, the seek commands and both handles; a fix to the static path regresses nothing in the
streaming path, so the discriminator is the OFF-diagonal cell, not a shared function. (2)
Interdependent: reverse x fade changes the wrap target that seek uses; rate x fade changes where the
blend happens relative to the resampler; streaming x fade changes what the scheduler must have
decoded before the window. (3) Not a standalone file: `Transport`, two `process` loops, the scheduler,
two settings, two handles and the command set all change. (4) The fundsp law: fundsp died because the
repo's own `FeedbackUnit` was an oracle and every agent adopted it. kira has no unit that reads two
positions; the nearest helper (`frame_at_index` on the scheduler) is the WRONG architecture for the
streaming path, which is the S5 shape that survived on stoolap. The blend math is trivial by design;
the band must come from the streaming pre-fetch, the reverse wrap and the exact-fit chunk
straddle, not from the arithmetic.

**Honest difficulty read:** 30-45%. Risk that a strong agent pulls the head frames through the
existing random-access path and passes every static test; the streaming discriminator must be a
stated observable (position, decoder cursor) rather than a performance claim.
