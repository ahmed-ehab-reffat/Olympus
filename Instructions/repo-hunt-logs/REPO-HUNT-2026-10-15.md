**Capability:**
- Each device reports, at the end of every sync, the set of document file checksums it still uses. Deleted documents and files not yet downloaded both count as in use.
- `micasa pro storage --reclaim` deletes relay blobs that no current report lists. It does so only once every active (non-revoked) device has reported since its own last push. Otherwise it names the devices it is waiting for.
- A replaced document file must reach every device.
- Outsider summary: "garbage-collect unreferenced encrypted blobs on micasa's sync relay, gated on every device's in-use report being newer than its last push". Generic blob GC is nameable (MEDIUM). The gating rule is repo-internal, and no issue or PR names it.

**Gate 1 (from code; runtime probe OWED):**
1. The relay `Store` has PutBlob/GetBlob/HasBlob/BlobUsage and no delete (`internal/relay/store.go:136-150`, memstore.go:593-672, pgstore.go:815-913). The handler routes only PUT/GET/HEAD for blobs (handler.go:80-90). A replaced file leaves the old blob counted against the 1 GiB quota forever.
2. **There is also a base bug, confirmed by reading HEAD:**
   - `applyUpdate` (apply.go:203-219) strips `blob_ref` and writes the new `sha256`, but keeps the old `data`.
   - `PendingBlobDocuments` (store_document.go:104-111) selects only `data IS NULL`.
   - So peers keep the old bytes under the new checksum.
   - **FP-ammo warning for the builder:** this is a reference fix of a base bug. Meta must state replaced-file propagation as a rule (memory "FP panel excuses shared gaps").

**Missing machinery:**
- per-device in-use reports in MemStore and PgStore, with the new PgStore table registered in `rlsTables`/`pgModels`;
- the freshness rule (report seq >= that device's last push seq);
- a sweep returning count, bytes freed, new usage and the waiting devices;
- two authenticated routes;
- client calls;
- the report step at the end of `Sync`;
- a checksum set that includes deleted documents;
- the apply fix;
- `pro storage --reclaim`.

**Written sketch:** `sketch_micasa_blobreclaim_h65.patch`, re-measured by me: **human-effective 328** (raw 465). By file: pgstore 109, memstore 55, handler 46, sync/blob 39, pro.go 30, engine 18, apply 14, store_document 8, types 7, store 2.
- The padding-floor reads 39. The patch has no repeated arm families, so this looks like a hook artefact; the human re-count is owed.
- Without PgStore it is about 219. PgStore must implement the new `Store` methods to compile, but its tests skip without `RELAY_POSTGRES_DSN`.

**Traps (interdependent, misdirecting):**
1. **What a device reports (F-47/F-78).** Deleted rows are hidden by GORM's default scope (models.go:293), and files not yet downloaded must count too. `PendingBlobDocuments` is the pattern an agent will copy. The failure shows up on a third device that joins after a restore.
2. **Where the report goes in Sync (F-9/F-15).** It must come after push and after the blob phase (engine.go:70-80). If it comes earlier, the device's own push is newer than its report, and the relay names a device that just synced as "waiting".
3. **Reused files never re-upload (F-41/F-39).** `uploadPendingBlobs` skips blobs the relay already has (engine.go:217-222), so freshness by blob upload time reclaims a file a new document uses. Shares the seq comparison with trap 2.
4. **Stale content after replacement (F-39).** This is the base bug above. It masks trap 1: a device holding stale bytes still reports the `sha256` column.
5. **F-10 cells:** revoked devices ignored; a device that has never synced blocks the reclaim; two documents sharing one file keep it. Existing engine and handler tests pin current behaviour (F-12-like p2p, e.g. `failingStore` at handler_test.go:1948).

It names ops, pending exchanges and invites, not blobs. That makes it adjacent: relay oplog compaction is dead on it, and blob reclaim is not named. It is a design doc, not a roadmap issue.
